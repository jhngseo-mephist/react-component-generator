# Commit

변경 의도가 드러나는 논리적 단위로 커밋하고, 실제 포함할 변경사항과 한국어 메시지를 사용자에게 먼저 보여준다.

## 1. 변경사항 분석

- `git rev-parse --show-toplevel`로 저장소를 확인한다. 저장소가 아니면 그 사실을 알리고 중단하며, 임의로 `git init`을 실행하지 않는다.
- 저장소의 적용 가능한 `AGENTS.md`와 커밋 규칙을 확인한다.
- `git status --short`, `git diff --stat`, `git diff`, `git diff --cached`로 미스테이징·스테이징 변경을 모두 검토한다. 추적되지 않은 파일은 필요한 내용을 별도로 확인한다.
- 변경사항이 없으면 커밋할 내용이 없다고 알리고 종료한다. 충돌이 남아 있으면 이를 알리고 커밋을 진행하지 않는다.
- 비밀값이나 API 키를 메시지·출력에 노출하거나 커밋에 포함하지 않는다.

## 2. 논리적 단위 분류

- 파일 수가 아니라 변경 목적을 기준으로 묶는다. 하나의 기능과 그에 필요한 테스트·문서는 같은 커밋으로 묶고, 독립적인 기능·버그 수정·정리는 분리한다.
- 사용자 작업과 기존 스테이징 상태를 존중한다. 요청 범위 밖의 변경을 임의로 포함하거나 되돌리지 않는다.
- 같은 파일에 서로 다른 목적의 변경이 섞여 있으면 필요한 부분만 선택적으로 스테이징할 계획을 세운다. 안전하게 분리하기 어렵다면 승인 전에 설명한다.
- 프로젝트에서 요구하거나 변경에 적합한 검증을 수행하고, 실패 또는 실행하지 못한 검증은 승인 제안에 명시한다.

## 3. 한국어 커밋 메시지 제안

형식: `type: 한국어 요약`

- `feat`: 새로운 기능이나 사용자에게 보이는 기능 개선
- `fix`: 잘못된 동작 수정
- `refactor`: 외부 동작을 유지하는 코드 구조 개선
- `chore`: 도구, 설정, 의존성, 문서 등 유지보수

요약은 변경의 결과가 드러나도록 간결하게 작성한다. 필요한 경우 본문에 이유와 주요 영향을 덧붙인다.

예시:

```text
feat: 컴포넌트 작업실에 레트로 테마 적용
fix: 빈 프롬프트의 생성 요청 방지
refactor: 제공자별 설정 처리 통합
chore: 커밋 작업 스킬 추가
```

커밋별로 포함할 파일·주요 변경, 정확한 메시지, 검증 결과를 제시하고 승인을 요청한다. 이 스킬의 "사용자 승인 후 커밋" 절차에 따른 요청임을 밝히고 현재 `SKILL.md`를 링크한다. 일반적인 "커밋해줘" 요청만으로 구체적인 커밋 계획이 승인되었다고 간주하지 않는다. 다만 같은 대화에서 해당 변경 범위와 메시지를 이미 명시적으로 승인했다면 다시 묻지 않는다.

## 4. 승인 후 커밋

- 승인된 범위와 메시지로만 진행한다. 거절되거나 응답이 없으면 커밋하지 않는다.
- 승인 후 diff를 다시 확인한다. 승인 이후 범위나 메시지가 실질적으로 바뀌었다면 변경된 계획에 대해 다시 승인받는다.
- 명시적인 파일 경로 또는 필요한 헝크만 스테이징한다. `git add .`로 관련 없는 변경을 포함하지 않는다.
- 각 커밋 직전에 `git diff --cached`로 실제 포함 내용을 확인한다. 기존 스테이징 내용이 승인 범위 밖이면 임의로 해제하거나 함께 커밋하지 않고 사용자에게 알린다.
- `git commit`을 실행한다. 여러 커밋이면 승인된 논리적 단위 순서대로 진행한다. 여러 줄 메시지는 임시 UTF-8 파일을 만들어 `git commit -F <파일>`로 전달한다.
- 훅이나 커밋이 실패하면 원인을 확인하고 알린다. 검증을 우회하거나 무관한 변경까지 수정하지 않는다.
- 완료 후 `git log -1 --oneline`, `git status --short`로 확인하고 생성한 커밋 해시·메시지와 남은 변경을 보고한다.
- 별도 요청 없이 push, amend, reset 또는 이력 재작성을 실행하지 않는다.
